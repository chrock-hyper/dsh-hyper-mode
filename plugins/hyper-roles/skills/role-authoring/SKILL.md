# 写一张岗位卡

岗位卡不是职位描述，而是**给 Agent 的执行约定**：它读完之后应该知道「我负责什么、不负责什么、东西交给谁、做到什么算完成、什么做法是错的」。写不好的卡片，Agent 会越界、会空转、会把活退回来。

## 完成标准

一张及格的卡片满足四条：

1. **边界可判定**：读完能说出「这事不归它管」。
2. **产物有形**：它交什么东西、交给谁、什么格式。
3. **完成可验收**：能判断做完没有，而不是「做好了」。
4. **反模式具体**：写的是行为（「把原话转给专家」），不是态度（「要认真」）。

## 前置

- 能改岗位：`role` / `role_edit` 两个工具可用。`role_edit` 要求调用方未绑定岗位，或绑定的岗位带 `edit-roles`（例如 `trainer`）。
- 先看现状：`role action=list` 看已有岗位，`role action=read role=<id>` 看一张卡的写法；避免重复造一个语义相同的岗位。
- 分清作用域：只对这个项目有效 → 项目作用域；通用岗位 → 全局。同名时项目覆盖全局。

## 提问协议

**一次只问一组，给选项而不是开放式问题。** 用户回答「不知道」时不要编，把它标成假设写进卡片的「待确认」里。

### 第一轮：五个问题，一次问完

用编号列出，允许用户只答一部分：

1. **这个岗位为谁解决什么问题？** 一句话，说清服务对象（用户 / 另一个岗位）与产出。
2. **它明确不做什么？** 划边界比列职责更有用：把相邻岗位的活指出来（「方案不归它」、「界面不归它」）。
3. **输入从谁来、输出交给谁？** 各举一个真实例子，包括产物形态（一页简报 / 一张卡 / 一份 diff）。
4. **它能自己拍板到什么程度？** 哪些必须回来问；卡住时升级给谁。
5. **怎么判断这件事做完了、而且做得好？** 要能观察的行为，不要「质量高」。

### 第二轮：按缺口追问，一次最多三个

| 缺口 | 追问 |
|---|---|
| 工作方式不清 | 它先做什么、后做什么？有没有不能跳的步骤？ |
| 判断标准不清 | 什么信号出现时该做哪种判断？举一个最近的真实例子。 |
| 反模式不清 | 你见过最差的做法是什么？为什么差？ |
| 汇报/交付不清 | 给谁看、多长、什么结构？ |
| 权限不清 | 它需要改岗位卡或写别人的经验吗？（`edit-roles` / `train`） |
| 协作不清 | 和哪些岗位交接？单向给还是互相给？ |

### 问法上的硬规则

- **不要替用户编职责。** 编出来的职责会让 Agent 在真实场景里做错事；宁可留一个显式的「待确认」。
- **不要一次问十个问题。** 用户会用「你看着办」结束对话，你拿到的是噪声。
- **用用户的词，不用你的词。** 用户说「对接」就不要改写成「需求管理」。
- 用户给了案例就抓案例：案例里它做对/做错了什么，比抽象描述更能定义岗位。

## 卡片结构

前后两段：frontmatter 是机器读的，正文是 Agent 读的。

```markdown
---
id: secretary
title: 秘书
version: 1
capabilities: 需求承接, 任务派发, 进度汇总
skills: role-training
handoffs: product-manager, architect
can: edit-roles
---

## 职责
一句话说清它负责什么、不负责什么。

## 工作方式
编号步骤；每步是可执行动作，不是原则。

## 交互对象
- 向上：谁给它任务、它向谁汇报。
- 平级：谁与它交接、交接什么。
- 资产：它写入什么（岗位笔记 / wiki / 代码）。

## 完成标准
可验证的条目，每条都能对着产物打勾。

## 反模式
具体行为，一条一句。
```

写作要求：

- 用**第二人称「你」**，像在跟这个岗位的人说话。
- **职责段**先写「你负责」，再写「你不做」——后者往往更重要。
- **工作方式**写触发条件与顺序（「先读现状，再给方案」），不要写「要专业」。
- **交互对象**必须与 frontmatter 的 `handoffs` 一致；不一致时以正文为准并修正字段。
- **完成标准**每条都能被第三方验收；出现「尽量」「看情况」就重写。
- **反模式**写你真实见过的坏做法，而不是「不要犯错」。
- 长度 30–60 行。超过说明职责没聚焦，回头砍范围。

## 写入与校验

1. `role_edit action=create id=<id> title=<标题> body=<正文>`；`id` 只能小写字母、数字与连字符。已存在则 `action=update`，带上读到的 `version`（否则会被判为过期）。
2. 字段用逗号分隔；`handoffs` 写岗位 id；`can` 只接受 `edit-roles` / `train`。
3. 写完用 `role action=read role=<id>` 复核：读一遍，问自己「一个没参与过讨论的 Agent 拿这张卡能直接开工吗？」不能就补。
4. 让用户看一眼再定稿：**用户确认的是边界与完成标准**，不是文笔。
5. 后续维护：这个岗位在真实案例里做错了，用 `role action=note` 追加一条经验（触发场景 → 判断 → 为什么），不要直接改卡片正文；卡片变更走 `role_edit` 并让用户知道。

## 反模式（写卡时）

- 一次问二十个问题，最后按自己的想象写。
- 把职责写成愿望（「让产品更好」）。
- 没有「不做什么」的岗位卡。
- 完成标准是「做好了 / 质量高 / 及时」。
- 复制一张现成卡片，只改标题。
- 把工具调用细节写进职责（职责是边界，不是操作手册）。
