# 岗位交叉培训

一次培训的产出不是"纪要"，而是**每个岗位的工作方式发生了可复述的改变**，以及一份可以被人审批成文的报告。

## 前置

- 有岗位目录：`role` 的 `action=list` 能看到参与岗位；没有就先建。
- 有案例材料：原文、上下文、以及这次想练的判断点。案例不清就先问，不要用"假设一个场景"替代真实案例。
- 确认自己以培训员岗位在跑（`role` 的 `action=brief` 能看到 trainer 卡片）。培训员需要作为根会话运行，否则拉不起同岗位级别的子代理。

## 步骤

### 1. 定框架（5 分钟以内）

写下来，再动手：

```
参与岗位：<id> × 3（2–4 个）
各自视角：<岗位> 看 <这一面>，因为 <它的职责>
统一维度：判据 / 边界条件 / 失败信号 / 可复用动作
输出格式：结论（3 条以内）· 依据 · 我以后会怎么改
```

框架不写清，后面收到的就是三段无法比较的文字。

### 2. 并行委派

对每个岗位调用 `role_spawn`，一次消息里发多个调用：

- `role`：岗位 id
- `description`：3–5 个词，说明这次要它看什么
- `prompt`：案例材料 + 它该看的那一面 + 统一维度 + 输出格式 + "不要复述案例，直接给判断"

子代理看不到你的对话，材料要自包含。岗位卡片由工具自动附加，不要在 prompt 里重复职责。

### 3. 摊平

收齐后按统一维度做三栏对照：

```
共识：大家判断一致的（这是团队基线）
分歧：判断不一致的（这是最值钱的部分——写清各自依据）
可复用技巧：某个岗位独有、但别人能直接用的动作
```

### 4. 回灌

用 `send_message` 把**其他岗位**的要点发给每个子代理，只问三件事：

1. 你会采纳哪几条？抄一句原文。
2. 你的工作方式要改哪一步（具体到动作）。
3. 哪些明显不适用？为什么。

没有第 3 问，回灌就会退化成互相点赞。

### 5. 落袋

- 子代理自己写：`role action=note text="…"`。
- 培训员代写（需要 `train`）：`role action=note role=<id> text="…"`。
- 每条经验写成「什么信号出现时 → 做什么判断 → 为什么」，不要写"要注意质量"这种不可执行的话。

### 6. 成文

用 `wiki` 的 `action=draft` 写报告，路径建议 `training/<YYYY-MM-DD>-<案例名>.md`：

```
title: <案例名> 培训记录
tags: training, <参与岗位>
---

## 案例
## 各岗位判断（按统一维度对照）
## 分歧与原因
## 被采纳的经验（逐岗位）
## 下次建议
```

草稿写完就停手：成文由人批准。不要绕过草稿直接写 `wiki/` 正文。

## 验收

- 每个岗位至少一条**带触发条件**的判据。
- 至少一条经验来自跨岗位迁移，并写清了改写后的形态。
- 报告草稿在 `wiki/drafts/` 下，人打开面板能看到 diff。
